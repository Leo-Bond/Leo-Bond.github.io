推荐模型 Scaling（四）：从 SID 生成到价值引导搜索

发表于 2026-10-12 更新于 2026-10-13 分类于 推荐系统
从 SID、NTP 和 Beam Search 理解生成式推荐，梳理 OneRecV2、反馈后训练、GPR、UniVA 及异步推理如何改变计算分配与候选形成。

再强的 Ranker，也无法把没有进入候选集的物品排到前面。继续加深排序网络，改善的是既有候选之间的比较，却不会自动扩大候选搜索范围。

Generative Scaling 改变的是候选如何形成：模型根据用户信息逐步生成物品编码，再通过搜索得到候选。在这条链路上，计算不仅可以用于更大的模型，还可以用于反馈后训练、实时价值估计，以及请求之前的异步推理。

来源与公式说明：本文依据《推荐模型 Scaling：为什么必须依赖 Model–System Co-design》第四章整理。各方法和实验口径均为该综述的转述，未逐篇重新核验。公式按原文明确的文字关系重建，属于解释性表示；不补写缺失的 PPO、Reward 或模型专用损失公式。文中的 OneRec 指原文相应工业方案，不将不同版本与早期 Session 级方案混成同一套实现。

1. 排序能力与候选形成能力是两个问题

设完整物品库为 V，召回阶段为用户 u 产生候选集合 C_u，Ranker 对其中的候选打分。根据原文关系，可简写为：

\[ \mathcal{C}_u\subseteq\mathcal{V},\qquad \operatorname{Result}_u= \operatorname{TopK}_{v\in\mathcal{C}_u}f(u,v). \]

从函数定义上，Ranker 也许能对任意物品计算分数。但复杂的 Target Attention 与交互网络无法在线逐个处理百万乃至更大的物品库，所以实际求解范围仍受召回限制。

生成式推荐不再只接收一个候选并输出反馈分数，而是生成物品的离散编码，再映射回物品。它同样没有穷举整个物品库，只是把搜索变成了编码空间中的逐步选择。

这种改变扩大了模型参与候选形成的范围，但不能直接证明它优于 ANN 召回或所有多阶段系统。

2. SID：把一个物品变成多个离散 Token

2.1 为什么不让每个 Item ID 都是一个输出类别？

若每个物品对应独立 Token，输出词表接近物品库大小，编号本身也不表达内容或协同相似性。

Semantic ID（SID）将一个物品表示为多个离散 Token 的组合。令编码长度为 m，每层 Token 来自对应 Codebook：

\[ \operatorname{SID}(v)=(c_1,\ldots,c_m),\qquad c_j\in\mathcal{K}_j. \]

模型依次预测各层 Token，完整编码再通过映射返回物品。组合编码是否具有有用的相似性，取决于 Tokenizer 的输入信息、表示空间和训练目标，而不是“拆成多个数字”自动带来的性质。

2.2 TIGER 与 OneRec 使用什么信息构建编码？

按原文介绍：

  • TIGER 从内容模型得到物品向量，再用 RQ-VAE 逐层量化；内容相近的物品可能共享部分编码。
  • OneRec 进一步引入协同关系，通过相似物品对对齐多模态表示，使消费关系相近的物品更容易获得相近编码。

Tokenizer 决定物品对应哪个 SID，推荐模型学习如何根据用户上下文预测 SID。两者的更新周期可以分开，但不能忽略版本一致性。

如果 Tokenizer 或 Codebook 改变，训练目标、在线模型、item–SID mapping 与合法编码集合都可能需要同步切换。另一个工程前提是明确完整编码的映射规则：若有碰撞，需要消歧或定义后续候选展开，不能默认量化天然产生唯一编码。

3.3 合法编码与业务合法性

并非所有 Token 组合都对应物品。一种做法是生成后过滤；另一种是把已注册 SID 放进 Trie，只允许扩展合法后继。

还要区分两层约束：

  • 编码是否合法、是否能映射到物品；
  • 物品在当前请求中是否可推荐，例如库存、定向和素材状态是否满足要求。

全局合法不代表请求级合法。业务约束可以参与请求级 Trie 构建或其他确定性过滤，而不是全部交给概率模型学习。

4. OneRecV2：把更多计算放到较短的目标侧

4.1 用户上下文与目标 SID 的长度差距

TIGER 展示了内容 SID、NTP 与 Beam Search 的基础链路。工业 OneRec 还需要处理用户画像、近期行为、强正反馈和压缩后的长期历史。

用户画像和行为属性并非全部变成 SID，仍可通过各自的 Embedding 与 Projection 输入 Encoder；SID 主要表示历史物品与目标物品。

原文介绍的 OneRecV2 计算分析配置包含 512 个 Context Token，但目标只有 3 个 SID Token。在所引 1B 配置中，OneRecV1 的 Context Encoding 约 338 GFLOPs，目标侧 Decoder 计算约 8.1 GFLOPs。

这里 Context Encoding 包括 Encoder 变换，以及 Decoder Cross-Attention 对上下文的 K/V Projection；这些数字不是任意 OneRec 模型的每请求通用成本。

关键问题是：如果两侧都继续加深，大量新增计算会落在几百个 Context Token 的反复变换上，而目标侧只有少量 Token。

4.2 Context Processor 直接提供各层 K/V

OneRecV2 先处理用户上下文，再直接产生各 Decoder 层读取的 K/V：

这样减少 Context Token 的多层 Transformer 变换与重复 K/V Projection，将较多 Block、FFN 和 MoE 容量放到较短的目标侧。

但上下文仍然被各层 Cross-Attention 读取，其存储与读取成本没有消失。原文称其为 Lazy Decoder-only，却不是通常把所有上下文拼进单一自回归序列的 Decoder-only Transformer。

这是一种计算分配：减少上下文的重复变换，不等于上下文不重要。

5. 生成概率能够排序，却不等于推荐价值

Beam Search 的累计 Log-Probability 既决定 Prefix 去留，也给完整 SID 一个初始顺序。原文将这种关系称为 Generation-as-Ranking。

统一的是候选生成与基于生成概率的早期排序，不能由此断言点击、转化、长期满意度和商业价值也被统一。

NTP 学习的行为日志已经经过旧系统的曝光与分发策略。高生成概率可能部分反映热门度、曝光机会或旧策略偏好，而不完全是当前用户的最优价值。

在合法候选集合中，用 V(u,v) 表示经过定义与校准的价值分数，二者可能给出不同答案：

\[ \arg\max_{v\in\mathcal{V}_{\mathrm{valid}}(u)} \log p_\theta(\operatorname{SID}(v)\mid H) \neq \arg\max_{v\in\mathcal{V}_{\mathrm{valid}}(u)}V(u,v). \]

这不是说它们必然不同，而是没有天然相等的保证。V 也不表示多种业务目标天然具有相同量纲，实际需要明确组合规则。

生成后再交给 Ranker 是一种可行方案，但后置模型无法挽回已在早期被剪掉的路径。若希望价值改变候选形成，就需要让它进入训练或搜索。

6. OneRec 与 OneRecV2：反馈先改变未来的生成分布

6.1 RSFT 改变继续训练的数据

原文所述的 OneRec 使用 Reject Sampling Fine-Tuning，按播放时长过滤后 50% 的曝光 Session，再对保留数据进行 NTP。

它首先改变的是训练分布：更符合筛选标准的样本获得后续学习机会。它不是在线搜索时给每条路径即时加分。

6.2 RL 用 Reward 更新生成 Policy

模型采样完整 SID，Reward System 评价生成结果，再更新 Policy。原文列出的 Reward 包括个性化点击、观看与互动目标，合法 SID，以及业务和生态目标。

这会增加 Rollout、Reward 计算与参数更新的成本。Reward 改变未来请求中的生成概率，并不意味着每个在线请求都重新运行 Reward Model。

6.3 OneRecV2 使用真实反馈，但不直接等同于原始播放时长

长视频天然更容易积累较长观看时间，所以原文描述的真实反馈构造包括：

  1. 按视频自身时长分桶；
  2. 在同一用户、相近视频时长的行为中计算播放时长分位数；
  3. 取高分位样本作为正反馈；
  4. 将显式 Dislike 作为负反馈；
  5. 过滤其余未进入正负集合的样本。

Reward Model 与这类真实反馈覆盖的目标不同，因此后者是补充来源，不是天然替代。真实反馈也来自实际曝光结果，不能自动消除曝光选择偏差。

三者共同点是：先更新模型参数，再影响后续请求的搜索分布。

7. GPR 与 UniVA：价值直接影响当前请求的搜索

这两类广告生成方案把 Value 放到 SID 尚未生成完成的阶段，但作用方式不同。

7.1 GPR：用 Prefix Value 分配展开机会

GPR 在生成模型之外估计当前请求状态下，某个 Prefix 继续生成可能取得的回报。

原文介绍的离线 Simulator 复现候选、特征处理、业务规则与价值模型，用 pCTR、pCVR 等模型为完整广告计算 Reward，同时训练生成 Policy 和 Prefix 估值能力。

上线后实时估值，并据此调整下一层搜索宽度：

  • 高 Value Prefix 获得更多展开机会；
  • 低 Value Prefix 获得较少预算；
  • 不满足请求约束的路径提前剪枝。

GPR 改变的是搜索预算流向，不是简单把 Value 与生成概率相加。额外估值本身也占用实时计算。

7.2 UniVA：价值与生成分数共同参与路径竞争

UniVA 在三个位置引入价值：

  1. 编码：前几层保留 Semantic SID，最后加入由行业、优化目标、ROI、Bid 等商业属性构造的 Commercial SID；
  2. 训练：共享 Decoder 后设置 Generation Head 与 Value Head，使用 Simulator 中的商业回报训练；
  3. 搜索：融合两组输出，使价值直接影响当前步骤保留的路径。

按原文“逐元素相加”的描述，可以写出分数融合示意：

\[ \boldsymbol{\ell}_{\mathrm{fused}} =\boldsymbol{\ell}_{\mathrm{gen}} +\boldsymbol{\ell}_{\mathrm{value}}. \]

两组向量对应同一层的下一 Token。这里是该方案训练出的两类 Logit 的融合关系，不能推广成“任意概率与任意业务分数直接相加”。

原文介绍其训练使用 Beam Search 和基于 MCTS 的探索产生轨迹，通过 PPO 类目标更新策略，并用逐层 Return 训练 Value Head；在线只执行 Beam Search，而不是在线运行 MCTS。

请求级 Trie 限制当前合法路径。Commercial SID 组织广告属性，Value Head 估计当前请求下的回报，Trie 处理合法性，三者职责不同。

它们都不能被简化为“生成以后再排序”。价值在完整候选形成之前就已经参与决策。

8. OneRecThink 与 OneReason：把较慢计算移出实时请求

价值估计不是唯一扩展方向。还可以增加兴趣分析与候选探索，但把较慢部分放在离线或近线阶段。

8.1 OneRecThink：缓存同一条 SID 的前半段

原文提醒：构造推理训练数据时已经知道目标物品，并围绕目标选择历史。因此这些文本更适合被看作目标相关的历史整理，不能当成模型真实决策过程的完整、忠实还原。

8.2 OneReason：独立产生候选，或向快模型提供监督

OneReason 是独立的推荐推理模型，连接自然语言与可以映射到物品的 Itemic Token。原文描述两种接入方式。

近线候选路线：生成完整 Itemic Token，解码成物品 ID，写入缓存；在线与实时 OneRec 候选合并，再交给后续 Ranker。

OneReason for OneRec：预测 Itemic Token，由量化模型得到对应 Embedding，作为对齐监督；通过 Alignment Network 对齐 OneRec Decoder 侧 BOS 的 hidden state，将知识与推理信号迁移给在线模型。实时请求仍由 OneRec 处理。

方法 慢阶段交付什么 在线如何使用
OneRecThink Reasoning 与 SID Prefix 根据最新行为补全 SID
OneReason 近线候选 完整物品候选 与实时候选合并后排序
OneReason for OneRec Itemic Token 对应的监督向量 通过训练迁移；线上由 OneRec 执行

三者不是仅仅模型大小不同，而是慢计算产生的结果及其与在线链路的连接方式不同。

9. Generative Scaling 的四份计算账单

扩展位置 改变什么 需要计量的成本
生成模型 每一步预测能力 活跃参数、解码 FLOPs、显存与延迟
后训练 后续请求的生成分布 样本筛选、训练更新、Rollout 和 Reward
在线搜索 当前候选路径的展开与保留 Beam、逐层 Value 推理、KV Cache
异步推理 提前准备兴趣、Prefix、候选或监督 推理资源、缓存、更新频率和新鲜度

把这四份账单全部写成“参数增加”，会遗漏大部分系统事实。相同模型可能通过更宽 Beam 增加实时成本，也可能通过更频繁的近线更新增加总资源消耗。

异步计算也不是免费：用户兴趣改变后要多久更新？缓存失效时如何降级？已经生成的候选是否仍满足库存与定向约束？这些问题必须跟模型方案一起设计。

10. 生成、价值与系统边界

生成式推荐确实把更多职责放进同一条 SID 链路：候选形成、基于概率的初始顺序，以及部分价值筛选。

但它不意味着一个物理模型替代了全部系统：Reward 可能来自独立模型，Simulator 可能复用已有 pCTR/pCVR，Prefix Value 可能单独估计，近线模型通过缓存或蒸馏连接，最终 Ranker 和确定性策略仍可保留。

判断一项 Generative Scaling 是否成立，需要分别回答：

  • 新增计算发生在训练、实时搜索还是异步阶段？
  • 收益来自模型扩容、反馈更新，还是更广的路径探索？
  • SID、映射与业务约束能否保持一致？
  • 效果是否足以抵偿延迟、缓存和更新成本？

回到 系列总览 的判断：Interaction、Sequence 与 Generative 是可以组合的方向，但不应不加区分地同时扩大所有模块。新增计算能否改善决策，需要实验验证；新增决策能否稳定上线，则取决于 Model–System Co-design。
