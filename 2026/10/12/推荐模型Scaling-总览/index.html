推荐模型 Scaling（一）：从参数规模到模型与系统协同设计

发表于 2026-10-12 更新于 2026-10-13 分类于 推荐系统
区分推荐模型的总参数、活跃计算、历史长度与搜索预算，从 GPU 执行效率出发建立 Interaction、Sequence、Generative 三条 Scaling 路线的分析框架。

推荐模型很早就拥有百亿乃至更大规模的 Embedding 参数，但这并不意味着一次请求已经执行了与总参数量相称的计算。把表做大、把交互网络加深、读取更长历史、展开更多生成路径，增加的是不同的成本，也不一定产生相同的收益。

这组文章围绕一个问题展开：新增计算究竟放在哪里，是否改善推荐效果，又能否被训练与线上服务系统以可接受的成本执行？ 本篇先建立分析框架，后三篇分别讨论特征交互、长序列与生成式推荐。

来源与阅读边界：本系列依据《推荐模型 Scaling：为什么必须依赖 Model–System Co-design》整理，本文对应原文第一章、第五章。原文公式未随正文完整导出；下文公式仅根据文字中明确给出的变量关系重建，用于解释，不是原始公式的逐字还原。涉及研究结果的表述来自该综述，未逐篇重新核验论文，也不代表独立复现实验。源文档需要相应访问权限。

  3. 长序列：从历史检索到多候选计算复用

1. 模型很大，不等于每次请求计算很多

推荐模型通常包含用户、物品、作者、类目等高基数类别特征。它们通过 Embedding Table 转换为向量，再进入后续网络。

设一张表有 N 行，每行 d 维；一次请求读取的行索引集合为 I。根据这三个定义，可以写出：

\[ E\in\mathbb{R}^{N\times d},\qquad P_{\mathrm{table}}=Nd,\qquad E_I\in\mathbb{R}^{|I|\times d}. \]

通常，一次请求涉及的行数远小于总行数。因此，下面三种扩展不能混在一起：

扩展对象 首先增加什么 不一定增加什么
表的行数 N 可保存的 ID 数量、参数存储 单次请求的 Lookup 数量和后续计算
每行维度 d 每次 Lookup 的数据量、输入向量宽度 若立即投影回固定维度，后续主干宽度未必增加
一次请求读取的行数 输入读取量，可能还有序列或交互计算 整张表的总参数量

如果只增加表的行数，但请求仍读取原来的少量 ID，那么模型总参数可能显著增长，单次前向计算却基本不变。

Dense Network 也不能只看总参数。普通 MLP 的权重通常每次前向都会使用；MoE 保存多个 Expert，但只执行路由选中的部分。于是，“模型有多少参数”至少应该拆成：

  • Embedding 与稠密网络分别存储多少参数；
  • 单次请求读取多少行、每行多宽；
  • 单次前向激活多少 Expert；
  • 最终执行多少 FLOPs。

Tokenizer、Reward Model 和近线推理模型还可能不在在线请求中运行。把所有模型的参数相加，更不能直接推出在线成本。

2. 理论 FLOPs 与 GPU 真正执行的工作

2.1 GPU 喜欢什么样的计算？

对这里讨论的主干计算而言，GPU 擅长较大、规整的矩阵乘法。用一层线性变换表示：

\[ Y=XW,\qquad X\in\mathbb{R}^{B\times d_{\mathrm{in}}},\quad W\in\mathbb{R}^{d_{\mathrm{in}}\times d_{\mathrm{out}}}. \]

B 表示共同计算的样本数，两个 d 分别表示输入与输出维度。足够的并行度和数据复用，有助于摊薄权重读取、Kernel 启动等成本。但不存在脱离硬件、精度和 Batch Size 的统一“大矩阵阈值”。

传统推荐链路经常同时包含：

  1. 从大规模表中零散读取 Embedding；
  2. 在 CPU、参数服务器和 GPU 之间传输数据；
  3. 处理长度差别很大的用户历史；
  4. 执行多个小型 MLP、Cross Layer、Gate 和任务塔；
  5. 对多个候选重复执行候选相关 Attention。

这些模块可能使 GPU 等待数据、启动小 Kernel、反复读写中间结果，而不是持续执行大规模矩阵计算。更多峰值算力并不会自动消除这些等待。

2.2 算术强度解释了为什么 FLOPs 不是全部

按原文对算术强度和 Roofline 的定义，令 F 为浮点运算量，Q 为指定存储层级之间的数据搬运字节数，则：

\[ AI=\frac{F}{Q},\qquad P_{\mathrm{attainable}}\leq \min\left(P_{\mathrm{peak}},\;BW\cdot AI\right). \]

其中，P 表示计算吞吐，BW 是相应存储层级的带宽。比较时必须使用一致的硬件与精度口径。

  • 算术强度较低时，即使计算单元空闲，也可能受数据搬运限制。
  • 算术强度较高时，更容易接近计算吞吐限制。
  • 通信、同步、负载不均和调度开销还可能进一步压低实际性能。

因此，这个模型用于理解瓶颈，而不是把任意推荐链路的延迟精确换算成一个公式。LLM 也有显存和通信瓶颈，尤其小 Batch 自回归生成时，不能把它简单看成“永远计算密集”。

2.3 MFU 只衡量执行效率，不衡量推荐价值

令一个训练 Step 的模型理论计算量为 F_step，耗时为 t_step，全部参与设备在相应精度下的峰值吞吐之和为 P_peak，可写出解释性的 MFU 定义：

\[ \mathrm{MFU}=\frac{F_{\mathrm{step}}} {t_{\mathrm{step}}P_{\mathrm{peak}}}. \]

低 MFU 可能意味着访存、通信、小矩阵、变长数据负载不均等问题。但高 MFU 不代表推荐效果一定好：反复对同一组特征执行大型 GEMM，可能很高效，却未必增加有效信息。

反过来，Target Attention 可能改善效果，但随着候选数增加，其计算仍可能超出线上预算。

FLOPs 回答算了多少，MFU 回答执行得怎样，推荐指标回答是否值得算。 三者不能互相替代。

3. 三条路线分别把计算放在哪里？

路线 主要问题 可扩展变量 典型系统约束
Interaction Scaling 已读取的特征如何继续交换信息 交互层数、宽度、向量数、Expert GEMM 形状、参数分片、中间结果和通信
Sequence Scaling 如何利用更多历史行为 读取长度、筛选规模、Query 数、网络深度 变长输入、Attention 范围、缓存、多候选复用
Generative Scaling 如何直接形成候选并引入价值 生成模型、后训练、Beam、价值估计、异步推理 自回归延迟、合法性约束、缓存更新与新鲜度

3.1 特征交互：让已经读到的信息算得更充分

这一方向从 Embedding Lookup 之后开始。DHEN 组合异构交互模块，Wukong 逐层重新计算两两交互，RankMixer 和 TokenMixer-Large 则通过固定重排交换向量片段，把主要非线性计算放在 Per-token 网络中。

问题不只是“能否继续加深”，还包括新增计算能否形成规整矩阵、参数怎样分片，以及存储中间结果需要多少显存。

3.2 长序列：历史更长不等于所有行为都经过深层网络

一个系统保存十万条历史，可能只筛选一百条进入精细建模；另一个模型可能让单个候选直接读取一万条历史，但不逐层更新全部历史向量。

所以必须分别报告：保存多少、读取多少、哪些参与计算、哪些结果能复用。 “支持十万长度”不能替代这些信息。

3.3 生成式推荐：计算从候选打分延伸到候选形成

Ranker 只比较召回阶段已经给出的候选。生成模型则逐 Token 输出物品的离散编码，通过搜索形成候选。

扩展不仅是增加模型参数，也可能是更多后训练、更多搜索分支、实时 Prefix Value，或更重的近线模型。这些计算发生在不同阶段，应该分别计量。

三条路线不是互相替代的年代顺序。生成模型也需要特征交互和长历史；OneTrans 联合建模序列与非序列特征，却仍然是给定候选后的排序模型。

4. Model–System Co-design 不是最后一步调优

小模型阶段，先确定结构，再优化执行，有时仍可接受。当显存、带宽和线上延迟接近上限，这种顺序就可能失效。

模型能读取多长历史、堆叠多少层、一次处理多少候选，以及保留多少 SID Prefix，都会受到系统约束。这意味着模型结构与执行方式需要一起确定：

想增加的能力 设计时就要回答的问题
更深的稠密主干 权重和优化器状态怎样分片？中间结果保存还是重算？
更长的历史 是否需要 Padding？Kernel 能否真正跳过无效区域？
更多候选 用户侧结果能否共享？Microbatch 如何影响显存和总耗时？
更大的生成搜索 路径如何批处理？KV Cache 怎样复用？合法性如何检查？
更重的近线推理 多久更新？过期结果怎么处理？缓存失败怎么降级？

这里的“协同”并不是要求所有计算都变成 GEMM，而是知道每类计算的目的、瓶颈和资源预算。

5. Scaling 的证据有多强？

原文区分了四个层次：

证据类型 能说明什么 还不能自动说明什么
Scaling Trend 已测试规模点中，效果随变量扩大继续改善 任意更大规模仍然改善
Empirical Scaling Curve 特定模型与数据条件下，存在可拟合关系 跨业务仍服从同一曲线
Scaling Law 经验证的关系能够预测未参与拟合的规模点 所有架构共享一个普遍规律
Compute-Optimal Scaling 固定预算下，变量如何配比更有效 训练与线上预算可以混成同一问题

这些不是简单的论文质量排名。对于工程团队，知道下一个规模点仍可能带来收益，本身就有价值；但需要避免把几张趋势图写成跨模型、跨数据的统一定律。

检验外推能力时，应使用较小配置拟合，再用未参与拟合的更大配置验证。若同时改变数据、结构、精度、候选数和 Kernel，结果可以证明整套方案有效，却不能独立证明某个变量的 Scaling 规律。

6. 如何设计一次有解释力的规模实验？

以下检查清单根据原文的评价框架整理，适合放在实验报告开头。

6.1 先定义扩大了什么

不要只写“从 1B 扩到 10B”。说明增加的是表行数、Dense 参数还是 Expert 总数，同时报告活跃参数和实际 FLOPs。

序列实验需要写清计数单位：行为、Item–Action Token、Cluster 或 Query。训练数据则区分 Session、交互记录、预测目标数、训练轮数，以及 RL 额外采样的轨迹。

6.2 分别固定训练预算与线上预算

固定训练资源时，选择可能是更大模型、更多数据、更长历史或更多 Rollout。

固定线上延迟时，选择则可能是更长历史、更多候选、更宽 Beam 或实时价值估计。这两组选择不是同一个优化问题。

推荐先明确一个预算口径，逐项变化，再观察质量与成本曲线；最后通过组合实验判断收益是否互补。

6.3 同时报效果、效率和稳定性

至少包含：

  • 离线 Loss、AUC、Recall 等与任务匹配的指标；
  • GPU 型号、数量、精度、训练时间与 MFU；
  • 线上延迟、吞吐、显存和通信成本；
  • 线上整体方案的收益，以及模型更新、降级和恢复能力。

还要说明复用条件。某份历史 KV 可以跨候选复用，不等于它能在任意后续请求中无限期复用；新行为、模型版本和特征变化都可能使缓存失效。

7. 结语：增加计算只是起点

推荐 Scaling 最有价值的变化，不是模型名称旁边出现了更大的参数数字，而是模型开始在特征交互、历史利用和候选形成上承担更多有效计算。

这些方向已经在各自测试范围内显示出继续扩展的空间，但计算能否持续带来收益，仍需要模型与系统共同回答：

模型决定计算增加在哪里；系统决定这些计算能否以可接受的成本运行；实验决定这些计算是否值得保留。
