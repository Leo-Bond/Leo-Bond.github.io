推荐模型 Scaling（三）：长序列建模与多候选计算复用

发表于 2026-10-12 更新于 2026-10-13 分类于 推荐系统
梳理 SIM、TWIN、HSTU、UltraHSTU、LONGER、STCA 与 OneTrans，区分历史保存、读取、实际计算和候选复用，理解长序列建模的系统代价。

“支持十万条用户历史”听起来比“支持一万条”更强，但两个数字可能描述完全不同的事情：前者也许只从十万条历史中筛出一百个簇，后者可能真的让每个候选读取一万条行为。

Sequence Scaling 的核心，不是让长度数字越来越大，而是决定：读取哪些历史、保留多少计算、哪些向量逐层更新，以及同一用户的多个候选能共享什么。

来源与公式说明：本文依据《推荐模型 Scaling：为什么必须依赖 Model–System Co-design》第三章整理。长度与配置数字均按综述转述，不是统一 Benchmark，也未逐篇重新核验论文。公式为依据原文文字定义的解释性重建，不包含未导出的模型专用 Attention、Mask 或训练损失细节。

1. 历史长度至少有四个口径

设用户按时间产生一组交互，每次交互由物品 v 和随后发生的动作 a 构成：

\[ \mathcal{H}_u=\big((v_1,a_1),\ldots,(v_L,a_L)\big). \]

动作可以是点击、播放、停留、转化等。对同一份历史，系统需要区分：

  1. 保存长度：存储系统保留了多少行为；
  2. 读取长度：一次请求实际取得多少行为；
  3. 计算长度：筛选、合并或截断后，哪些行为进入哪些网络层；
  4. 复用粒度：用户侧结果能否在候选之间或请求之间复用。

“计算长度”甚至不是一个固定数字。一层可能读取几千个 Key/Value，却只输出十几个 Query；深层网络又可能只处理这些输出。

本篇将方法分为三组：先检索再建模、扩大序列主干、用少量 Query 读取历史。这是计算方式的分类，不是论文之间的单向演进关系。

2. SIM、TWIN 与 TWINv2：先决定哪些历史值得精算

2.1 Target Attention 的收益与代价

不同候选需要不同历史证据。候选是相机时，数码行为可能更重要；候选是运动鞋时，运动和鞋服行为可能更有参考价值。

把历史编码为 K、V，把候选映射为 q，可用抽象操作表示：

\[ h_{u,v}=\operatorname{TargetAttention}(q_v,K_u,V_u). \]

这个记号只表达“候选读取历史”，不指定各论文的具体打分函数。完整历史越长、候选越多，数据读取和候选相关计算越重。

这些数字表示不同位置的长度。ESU 并没有处理完整的 54,000 条行为。 两阶段节约计算，却可能因为 GSU 与 ESU 的相关性标准不同，提前删掉精细模型真正需要的行为。

2.3 TWIN：让粗筛与精排使用一致的相关性标准

TWIN 仍保留 GSU/ESU，但让两阶段使用同一套候选—历史相关性模块。原文转述的配置是从最近 10,000 条行为中选择 100 条进入 ESU。

它的关键不是取消筛选，而是减轻“前一阶段认为不重要，后一阶段却需要”的错配。

这类方法扩大了可检索范围，但效果会同时受聚类与筛选质量影响。历史保存得更多，并不保证新增行为一定进入最终计算。

3. HSTU：用 Item–Action 序列组织多个预测目标

3.1 从独立曝光转向共享历史前缀

传统 Ranking 为相邻曝光分别构造样本时，通常会重复编码大段相同历史。HSTU 将连续交互写成 Item 与 Action 交错的因果序列：

\[ v_1,a_1,v_2,a_2,\ldots,v_L,a_L. \]

在历史基础上给定当前物品，预测随后的动作，对应 Ranking；观测动作后预测下一物品，可以用于 Retrieval。根据原文对两种任务的描述，可写成条件概率示意：

\[ p(a_t\mid\mathcal{H}_{这些表达不是完整训练目标，也没有指定正反馈采样方式。它们说明：一段因果序列可以在多个位置产生监督目标，共享的历史前缀不必为每个目标从头计算。

HSTU 因而尝试将 Retrieval 与 Ranking 组织成统一的 transduction 任务。但共享时间线和 Backbone，不代表线上求解方式完全相同：召回要从大物品空间形成候选，排序则预测已给候选的反馈。

3.2 长序列主干必须配套执行优化

原文列出的最大测试配置包含 8,192 个 Item–Action Token、24 层 HSTU，隐藏维度为 1,024。注意，交错 Token 数不等于行为次数。

HSTU 还调整了 Attention、门控、归一化和相对时间信息。这些专用结构不能仅用标准 Transformer 的 Softmax Attention 公式替代；本篇只讨论可从正文确认的执行机制。

4. HSTU 的三类关键系统设计

4.1 Jagged Tensor：不让短历史承担长历史的 Padding

但把数据存成这种格式还不够。Attention、Mask、相对时间处理和 GPU Kernel 都必须识别边界；如果后续又恢复成统一 Padding，主要收益可能被抵消。

Grouped GEMM 与变长 Attention 的实现，使不同长度的真实输入能够被组织为有效计算，而不是在模型外层补零后统一处理。

4.2 Stochastic Length：缩短训练时的平均序列

少数极长样本会抬高训练 Step 的计算量，也可能使不同 GPU 负载不均。Stochastic Length 通过采样较短子序列降低平均成本。

原文举例：4,096 个 Item–Action Token 的输入，在多数训练 Step 中采样到 776 个，减少超过 80% 的输入 Token。

这是训练阶段的采样策略，不能据此断言线上每次请求也只处理 776 个 Token，或端到端延迟降低同样比例。

4.3 M-FALCON：共享历史缓存，分批处理候选

用户历史的 Key/Value 与候选无关时可以缓存，但候选自身投影、读取历史的 Attention 和输出层仍需执行。

当候选太多，单次前向的显存或执行时间不可接受时，M-FALCON 将候选分成多个 Microbatch：

Mask 允许各候选读取历史，但不允许候选相互读取。不同候选组共享历史缓存，不因为分批而重复编码完整历史。

Microbatch 控制的是单次执行的规模，并不消除总候选计算。 候选数增加时，批次数和总工作量仍会增加；分批也不自动保证请求总延迟更低。

5. MTGR：保留工业特征的判别式 Ranking

MTGR 使用 HSTU-style Encoder，但保留候选特征、人工交叉特征和判别式目标。它把同一请求的候选聚合进一条输入，使用户画像和历史只编码一次。

原文介绍的输入最多包含 1,000 条长期历史和 100 条实时行为。实时行为可能发生在不同曝光之间，因此仅按某个拼接顺序做普通因果 Mask，不一定符合真实事件时间。

Dynamic Mask 控制三类关系：

  • 请求前已发生的用户画像与长期历史，对候选可见；
  • 实时行为按发生时间决定对相应候选是否可见；
  • 候选只能读取自己的候选特征，不能读取其他候选。

此外，不同语义组使用不同归一化参数，适应画像、历史、实时行为和候选输入的分布差异。

这说明两个问题可以分开：采用 HSTU 风格的序列主干，并不必然要求同时把召回与排序统一为 transduction。

6. UltraHSTU：降低每层和深层处理长历史的成本

UltraHSTU 同样聚焦给定候选后的 Ranking，保留 HSTU-style Self-Attention，同时从 Token、可见范围和逐层长度三个方面控制成本。

6.1 合并 Item 与 Action

一次已发生的交互不再展开成两个 Token，而是把物品与动作合并。待评分候选还没有真实动作，其 Action Embedding 使用零向量。

若 L 次交互从约 2L 个 Token 变为约 L 个 Token，则仅就两两 Attention 项而言：

\[ (2L)^2=4L^2\quad\longrightarrow\quad L^2. \]

这是按原文长度关系重建的量级比较。它不代表整个模型 FLOPs、显存或线上延迟都变为四分之一。

6.2 Semi-Local Attention：减少每个 Query 可读的区域

历史 Token 仍作为 Query，但只读取指定的 Local Window 和 Global Window。用 W_local、W_global 表示两类窗口大小，d 表示相应 Attention 宽度，可将主要交互项概括为：

\[ O(L^2d)\quad\longrightarrow\quad O\big(L(W_{\mathrm{local}}+W_{\mathrm{global}})d\big). \]

这是忽略投影、FFN 和常数的复杂度示意；只有窗口大小不随 L 同比例增长时，才具有关于长度的近似线性关系。

更重要的是，Kernel 必须真正跳过 Mask 外的块。如果仍计算完整矩阵，再把不可见位置屏蔽掉，主要计算并不会因此降为线性。

6.3 Attention Truncation：后面不再更新全部历史

较长历史先通过前几个 Block，再只保留近期部分进入更深的 Block。原文给出的截断消融配置是从 3,072 个历史 Token 保留最近 512 个。

它减少深层更新的向量数，但不是“更深层仍然逐 Token 访问所有原始历史”。保留下来的表示可能已经聚合部分早期信息，直接输入范围却已经改变。

6.4 Mixture of Transducers：分开建模不同行为流

播放和浏览数量大，点赞、评论和分享相对稀疏。如果共用同一长度预算，高频行为可能挤占稀疏但强意图行为的位置。

UltraHSTU 将不同类型行为交给独立 Transducer，再融合结果。这里的 Mixture 不是标准 MoE 的稀疏 Expert 路由，而是行为流拆分。

代价是：不同行为不再从第一层起就在同一条时间线上交互。是否值得，需要通过效果与成本验证。

6.5 结构收益需要 Kernel 和显存策略实现

原文列出的配套措施包括负载均衡的 Stochastic Length、专用 Semi-Local Kernel、GEMM 的 FP8、Serving Embedding 传输的 INT4、重计算以及全链路 Jagged Tensor。

原文报告的工业测试范围达到 16,384 个历史 Token、最多 18 层。它说明了该配置下的可扩展性，而不是所有长序列 Ranker 都能直接复现的上限。

7. LONGER 与 STCA：不必反复更新所有历史向量

7.1 LONGER：先合并历史，再压缩为少量 Query 输出

LONGER 先通过 Token Merge 合并相邻行为，缩短 Key/Value；再由 Global Token 和少量历史 Token 作为 Query，读取合并后的历史。

后续深层网络只更新这组较少的输出，而不是每层重新更新全部历史。

7.2 STCA：只逐层更新候选 Query

STCA 将候选作为唯一 Query，逐层读取历史 K/V；下一层 Query 由候选与前面层的输出共同形成。历史编码结果只作为被读取的对象，不像完整 Self-Attention 那样逐层更新全部历史位置。

对固定 d 和单个 Query，Cross-Attention 的主要交互项随历史长度线性增长。但多个候选、多个层仍然会增加总成本。

原文转述的配置是训练平均约 2,000 条历史、线上最多 10,000 条，并通过 Request Level Batching 组织同一请求的候选，复用历史读取。

LONGER 与 STCA 都减少了深层更新的向量数，却采用不同结构。它们也不一定优于 Self-Attention：节约计算的同时，历史行为之间直接交互的方式发生了变化。

8. OneTrans：在同一主干中建模序列与非序列特征

传统 Ranker 常先用独立序列编码器得到兴趣表示，再送进另一套交互网络。OneTrans 把两类输入放进同一个 Transformer Backbone：

  • S-Token：用户行为序列；
  • NS-Token：用户非序列信息、候选、上下文和人工交叉特征。

8.1 同一 Backbone 不等于全部参数共享

S-Token 共享一套 Q/K/V 与 FFN 参数；各 NS-Token 使用对应位置的投影和 FFN 参数。

这与 MTGR 为语义组分别归一化不同：两者都处理异构输入，但参数区分发生的位置并不相同。

8.2 Pyramid Stack：逐层缩短输入

每层只为保留的 Query 计算输出，这些 Query 读取当前层输入；输出成为下一层更短的输入，没有保留的位置不再进入下一层。

原文列出 OneTrans-S 从 1,190 个 S-Token 缩至 12 个 Query，OneTrans-L 从 1,500 个缩至 16 个。

这与 LONGER 一次压缩到少量 Query 的方式不同：OneTrans 在多个 Block 间继续缩减。不能把两者写成必然的继承或替代关系。

8.3 因果依赖决定能否缓存

S-Token 放在 NS-Token 前，配合 Causal Mask，使历史表示不依赖候选，而候选相关 Token 可以读取历史。用户侧 K/V 因此具备跨候选复用的条件。

跨请求复用还要检查新行为、模型版本、时间特征等是否改变历史计算。缓存可复用是有条件的，不是只要保存过就永久有效。

OneTrans 统一的是 Ranker 内部的序列与非序列建模，仍然接收给定候选并输出分数，不应被归类为直接生成候选。

10. 结语：长历史是一种资源分配问题

Sequence Scaling 至少有三种有效做法：从更多历史中选出有用部分，让更多历史进入序列主干，或者用更少的 Query 读取更长历史。

它们都需要与系统共同设计：Jagged 减少 Padding，稀疏 Kernel 跳过无效区域，缓存减少重复用户侧计算，Microbatch 控制候选执行规模。但这些策略都没有消除数据读取、候选计算和更新成本。

最后还要区分两件事：模型是否利用了更多历史，与模型是否直接形成候选，不是同一个问题。 下一篇 Generative Scaling 将从候选产生方式切入，讨论 SID、搜索与价值对齐。
